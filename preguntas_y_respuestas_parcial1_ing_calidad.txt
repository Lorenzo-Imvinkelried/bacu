PREGUNTA 2 (ID: ing-cal-p1-q2) | Tipo: Selección Única | Puntaje: 1.00 ptos.
Tópico / Unidad: Gestión de Configuración (SCM)

ENUNCIADO:
Un proyecto de software en el que se está utilizando una herramienta de gestión de versiones, dispone en un momento determinado T de una rama ‘principal’ P. Se aprueba la realización de un cambio en el elemento E (que forma parte de la rama principal P). Las acciones a tomar son:

OPCIONES:
  [1] (1) Comenzar a aplicar el cambio en la rama principal P.
  [2] (1) Buscar la última rama ‘secundaria’ creada y (2) Trabajar en ésta el cambio requerido.
  [3] (1) Crear una nueva rama B a partir de la rama principal P para trabajar el cambio E. (2) Cuando este esté listo, probado y aprobado, se agregan a la rama P.  <--- [CORRECTA]
  [4] (1) Trabajar el cambio por fuera de la herramienta de gestión de versiones, y (2) Cuando este esté listo para probar, se agregan a la rama P.

RESPUESTA(S) CORRECTA(S):
  -> Opción [3]: (1) Crear una nueva rama B a partir de la rama principal P para trabajar el cambio E. (2) Cuando este esté listo, probado y aprobado, se agregan a la rama P.

JUSTIFICACIÓN / EXPLICACIÓN DE CÁTEDRA:
En un flujo de trabajo con control de versiones (como Git), para modificar un elemento de la rama principal se debe crear una nueva rama (branch) a partir de ella, realizar y probar el cambio allí, y una vez aprobado, integrarlo (merge) a la rama principal.

ENUNCIADO:
En el marco de la identificación de versiones bajo 'Versionado Semántico' (SemVer con formato X.Y.Z o MAJOR.MINOR.PATCH), ¿qué significado tiene un incremento en el número MAJOR (X.0.0)?

OPCIONES:
  [a] Se introducen cambios mayores en la API que generan incompatibilidad con versiones anteriores (breaking changes).  <--- [CORRECTA]
  [b] Se corrigen errores o bugs menores manteniendo total compatibilidad hacia atrás.
  [c] Se agrega nueva funcionalidad manteniendo compatibilidad hacia atrás.
  [d] Indica un contador simple de compilaciones diarias generado automáticamente por la herramienta de integración continua.

RESPUESTA(S) CORRECTA(S):
  -> Opción [a]: Se introducen cambios mayores en la API que generan incompatibilidad con versiones anteriores (breaking changes).

JUSTIFICACIÓN / EXPLICACIÓN DE CÁTEDRA:
En SemVer: MAJOR se incrementa cuando se realizan cambios incompatibles en la API; MINOR cuando se añade funcionalidad compatible; PATCH cuando se corrigen errores compatibles hacia atrás.

Tópico / Unidad: Naturaleza del Software

ENUNCIADO:
¿Por qué se sostiene formalmente en la Ingeniería de Software que el software no se 'manufactura' en el sentido clásico industrial?

OPCIONES:
  [a] Porque los mayores costos y esfuerzos de calidad radican en el diseño y desarrollo conceptual, mientras que la replicación o copia física del software tiene costo y esfuerzo marginales casi nulos.  <--- [CORRECTA]
  [b] Porque el software carece por completo de etapas de prueba, control de calidad y validación formal.
  [c] Porque el software nunca puede ser comercializado como un producto final ni vendido a usuarios.
  [d] Porque requiere ensamblaje de piezas mecánicas en líneas de montaje industriales automatizadas.

RESPUESTA(S) CORRECTA(S):
  -> Opción [a]: Porque los mayores costos y esfuerzos de calidad radican en el diseño y desarrollo conceptual, mientras que la replicación o copia física del software tiene costo y esfuerzo marginales casi nulos.

JUSTIFICACIÓN / EXPLICACIÓN DE CÁTEDRA:
Pressman y Sommerville destacan que el software se desarrolla o construye mediante ingeniería conceptual, no se manufactura. Una vez creado, crear millones de copias tiene un costo casi cero y no depende de materias primas físicas.

ENUNCIADO:
En Git, tras editar un archivo en la rama 'Branch1', ¿qué secuencia de comandos se debe ejecutar para agregarlo al control de versiones, guardarlo localmente y compartirlo en el repositorio remoto?

OPCIONES:
  [a] 1) git add <archivo>  2) git commit -m 'mensaje de cambio'  3) git push origin Branch1  <--- [CORRECTA]
  [b] 1) git push origin Branch1  2) git add .  3) git status
  [c] 1) git clone origin Branch1  2) git branch -D Branch1
  [d] 1) git checkout master  2) git reset --hard  3) git pull
